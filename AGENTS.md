# Правила разработки Coffie Bot

## Границы продукта

- Это автономный шаблон для одной кофейни. Не добавлять multi-tenancy, SaaS-биллинг, общую базу клиентов, микросервисы, Kubernetes или API Gateway.
- Допускается несколько физических точек одной кофейни, но не несколько независимых организаций.
- Все данные бренда, контакты, правила программ, изображения и тексты клиента должны находиться в конфигурации, seed-данных или базе, а не в бизнес-логике.
- Не добавлять оплату, заказы, кассовые интеграции, OCR чеков и встроенную обработку чаевых без отдельного решения владельца проекта.

## Архитектура

- Backend — модульный монолит. FastAPI routes, aiogram handlers и CLI только валидируют ввод, вызывают сервисы и преобразуют результат.
- HTTP API, Telegram-бот и worker используют один слой бизнес-логики и одну реляционную модель.
- Не смешивать transport-код, SQL-доступ и бизнес-правила. Репозитории отвечают за запросы, сервисы — за сценарии и инварианты.
- Публичный API версионируется под `/api/v1`; несовместимые изменения требуют миграционного плана.
- Новая зависимость должна решать конкретную задачу, быть совместимой с закреплёнными версиями и не дублировать стандартные возможности стека.

## Целостность данных

- Журналы операций и аудита не удалять и не переписывать. Отмена — новая компенсирующая операция со ссылкой на исходную.
- Изменение баланса, состояния лояльности, награды и журналов выполняется в одной транзакции БД.
- Опасные команды обязаны иметь idempotency key и уникальное ограничение на уровне PostgreSQL.
- Для конкурентных изменений блокировать текущее состояние пользователя (`SELECT ... FOR UPDATE`) и повторно проверять инварианты внутри транзакции.
- Текущий баланс — оптимизированный снимок; источником объяснения остаётся неизменяемый журнал.
- Деньги хранить целым числом минимальных единиц валюты, баллы и штампы — целыми числами, время — UTC. Бизнес-день рассчитывать на backend с часовым поясом настройки.
- Миграции Alembic должны быть прямыми и совместимыми с существующими установками. Не редактировать уже выпущенную миграцию ради изменения схемы — добавлять следующую.

## Безопасность

- Не доверять Telegram ID, роли, permission, балансу или результату расчёта от frontend. Проверять Telegram init data, срок её жизни и все права на backend.
- Каждый endpoint с объектом пользователя обязан предотвращать IDOR и отдавать только необходимые поля.
- Сессионные токены хранить в БД только в виде хеша; секреты — только в окружении. Не логировать bot token, init data, session token и приватные env-значения.
- QR содержит только случайный непрозрачный идентификатор. Telegram ID в QR запрещён. Перевыпуск отзывает предыдущую карту.
- Uploads проверять по фактическому MIME/сигнатуре и размеру, запрещать SVG/исполняемые форматы, генерировать серверное имя и исключать path traversal.
- Административные действия, неуспешные проверки прав и подозрительные попытки фиксировать как структурированные audit events.

## Роли

- `customer`: только собственные данные и публичный контент.
- `staff`: операции с клиентами только при наличии соответствующего permission; без произвольных корректировок и управления другими сотрудниками.
- `admin`: staff-действия, клиенты, контент, настройки программ, события и рассылки. Не назначает и не снимает администраторов.
- `owner`: все права, назначение администраторов, критические настройки и экспорт.
- Отключение сотрудника прекращает доступ и активные сессии, но не удаляет историю.

## Качество и рабочий процесс

- Перед изменением изучить README, этот файл, релевантный модуль, миграции и тесты.
- Для исправления ошибки сначала проследить сценарий от transport-слоя до commit/уведомления; успешный HTTP-ответ сам по себе не доказывает корректность операции.
- Для новой бизнес-логики добавлять unit-тесты; для транзакций, ролей, идемпотентности и API — integration-тесты; для критических экранов — frontend-тесты.
- После изменений запускать релевантные `make`/`npm` проверки. Перед завершением этапа — lint, format check, typecheck и тесты соответствующей части.
- Не утверждать, что команда прошла, если она не запускалась. Ограничения окружения и непроверенные сценарии указывать явно.
- Не коммитить `.env`, токены, дампы БД, пользовательские media, coverage и build artifacts.
- Не удалять или перезаписывать пользовательские изменения в dirty worktree.
