# Menu and pricing V2

> Статус: Phase 3 реализована локально. Production upgrade разрешается только
> после merge и успешного CI целевой ветки.

Phase 3 делает меню принадлежащим конкретному `Venue`, добавляет универсальные
модификаторы и детерминированный server-side расчёт корзины. Она намеренно не
создаёт заказ: неизменяемый snapshot результата этого расчёта сохраняется моделью
заказа в Phase 4.

## Владение меню

- `MenuCategory`, `MenuItem`, `ModifierGroup` и `Promotion` принадлежат одному
  `Venue` внутри организации.
- Composite foreign keys не позволяют связать товар, категорию и группу
  модификаторов из разных заведений.
- Новые admin-клиенты передают `venue_id` явно. Для обратной совместимости create
  категории/акции без него использует default active venue, затем сохраняет уже
  разрешённый UUID.
- Public menu можно фильтровать по `venue_id`; архивные, скрытые и недоступные
  сущности не участвуют в расчёте.

## Модификаторы

`ModifierGroup` задаёт минимальное/максимальное число выборов и обязательность.
`ModifierOption` задаёт server-side доплату, возможность количества и его максимум.
Одна группа может быть связана с несколькими товарами своего заведения.

Поддержаны выбор одного молока, несколько сиропов, количество сахара и
boolean-добавки. Клиент отправляет только `option_id` и количество. Название и цена
из frontend игнорируются: backend загружает актуальный каталог и повторно проверяет
доступность, принадлежность товару, min/max и quantity policy.

## Акции

Pricing rule является расширением существующей карточки `Promotion`. Поддержаны:

- percentage в basis points и fixed discount в minor units;
- период дат, дни недели и локальное время заведения, включая окно через полночь;
- pickup/delivery, минимальная сумма и birthday-only;
- targeting по категориям или товарам;
- priority, выбор большей выгоды при равном приоритете и явная stackability.

Акции сортируются детерминированно. Несуммируемая акция завершает подбор, а две
акции суммируются только если обе это разрешают. Скидка никогда не делает итог
отрицательным.

## Pricing API

`POST /api/v1/cart/price` принимает fulfillment mode и строки корзины. Для каждой
строки возвращаются snapshot-ready названия, базовая цена, выбранные модификаторы,
subtotal/discount/total и применённые акции. Смешанная корзина делится на части по
venue, после чего агрегируется в общий итог.

Admin API под `/api/v1/admin/pricing` управляет группами модификаторов и pricing
rules акций. Изменения пишут структурированный audit. Архивация группы обратима;
исторические заказы в следующей фазе будут читать собственный snapshot, а не
изменившийся каталог.

## Инварианты для Phase 4

- создание заказа обязано вызвать тот же `CartPricingService` внутри транзакции;
- итог, строки, modifier/promotion snapshots и venue split сохраняются в заказе;
- frontend total не принимается как источник истины;
- изменение меню или акции после create не меняет старый заказ;
- использование баллов рассчитывается отдельно поверх каждой venue-части.

## Проверка

Основная логика покрыта pure unit-тестами. PostgreSQL integration test доказывает
загрузку trusted каталога, venue promotion и отказ от поддельного `option_id`.
Migration `0012` проверяется на чистой базе, через Alembic parity и повторный seed.
Frontend имеет отдельный тест создания группы с привязкой к товару и доплатой.
